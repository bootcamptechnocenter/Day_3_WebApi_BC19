# PostgreSQL + EF Core (reference example)

`ICustomerRepository` has two implementations:

| Provider | Class | Data access |
|---|---|---|
| `Oracle` (default) | `Infrastructure/OracleCustomerRepository.cs` | Dapper + hand-written SQL |
| `Postgres` | `Infrastructure/Postgres/EfCustomerRepository.cs` | EF Core + LINQ |

Compare the two files: same interface, same behavior (paging, keyword, unique NIK, max 1000 ids), different style.

Only customers have a Postgres version. Applications (`/api/applications`), `/_dbping` and `/_tx-demo`
are Oracle-only. With `Database:Provider = Postgres` none of them is mapped (they return 404):
`Program.cs` registers the applications service/repository only for Oracle and removes
`ApplicationsController` from MVC.

## Files

```
Infrastructure/Postgres/
  AppDbContext.cs           DbContext with DbSet<Customer>; applies every IEntityTypeConfiguration in the assembly
  CustomerConfiguration.cs  table/column mapping: easycredit.customers, snake_case columns, unique index on nik
  EfCustomerRepository.cs   ICustomerRepository via EF Core
  AppDbContextFactory.cs    used only by `dotnet ef` at design time (does not start the web host, needs no Oracle/JWT config)
  Migrations/               generated by `dotnet ef`; commit these
db/postgres/
  schema.sql                idempotent SQL generated from the migrations (for DBAs / production)
  seed.sql                  3 sample customers
```

## One-time setup

```bash
# EF Core CLI (once per machine)
dotnet tool install --global dotnet-ef
# later, to upgrade:
dotnet tool update --global dotnet-ef

# Local Postgres in Docker
docker run --name pg-easycredit -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=easycredit -p 5432:5432 -d postgres:17

# Real connection string: keep it out of appsettings.json
dotnet user-secrets set "ConnectionStrings:Postgres" "Host=localhost;Port=5432;Database=easycredit;Username=postgres;Password=<pwd>"
# or: export ConnectionStrings__Postgres="Host=...;Password=<pwd>"
```

`appsettings.json` only holds a placeholder with an empty password. `dotnet ef` reads the connection
string through `AppDbContextFactory`, from (later wins): `appsettings.json`, `appsettings.Local.json`,
user-secrets, environment variables.

## Migration commands

| Command | What it does |
|---|---|
| `dotnet ef migrations add InitialCreate --context AppDbContext --output-dir Infrastructure/Postgres/Migrations` | Compares the model (DbContext + configurations) with the last snapshot and generates C# for the difference. First time: creates everything. Does not touch the database. |
| `dotnet ef database update --context AppDbContext` | Applies every migration not yet applied to the database in `ConnectionStrings:Postgres`. |
| `dotnet ef migrations add AddCustomerAddress --context AppDbContext --output-dir Infrastructure/Postgres/Migrations` | After changing an entity or configuration: generates a new migration for just that change. Run `dotnet ef database update` again to apply it. |
| `dotnet ef migrations remove --context AppDbContext` | Deletes the last migration, only if it has **not** been applied yet. If it was applied, roll the database back first (next row). |
| `dotnet ef database update InitialCreate` | Moves the database to an earlier migration by running the `Down()` methods of every migration after `InitialCreate`. `dotnet ef database update 0` undoes everything. |
| `dotnet ef migrations script --idempotent --context AppDbContext -o db/postgres/schema.sql` | Writes SQL instead of touching the database. `--idempotent` wraps each migration in an "already applied?" check, so the script is safe to run against any version. Use this for DBAs / production. |
| `dotnet ef migrations list` | Lists every migration and whether it is applied (needs a database connection). |

After `database update`, load the sample data:

```bash
docker exec -i pg-easycredit psql -U postgres -d easycredit < db/postgres/seed.sql
```

## How migrations work

- A migration is a C# file with `Up()` (apply) and `Down()` (undo), plus a `.Designer.cs` file.
  `AppDbContextModelSnapshot.cs` is the model as of the latest migration; `migrations add` diffs against it.
  **Commit all three** (the migrations and the snapshot). Without the snapshot the next migration recreates everything.
- `database update` records each applied migration in the `__EFMigrationsHistory` table
  (in the `public` schema). That table is how EF knows what is already applied.
- The `easycredit` schema is created by the first migration (`EnsureSchema("easycredit")` in `InitialCreate`).
- The app does **not** call `Database.Migrate()` at startup. Applying migrations is a deliberate,
  manual step, so a deploy never changes a schema by surprise, and production can apply `schema.sql`
  through its normal review.

## Notes on the mapping

- `CreatedAt` uses column type `timestamp` (without time zone). `Customer.CreatedAt` defaults to
  `DateTime.Now` (`Kind = Local`), and Npgsql refuses to write a non-UTC `DateTime` to
  `timestamp with time zone`.
- Keyword search uses `EF.Functions.ILike` (case-insensitive `LIKE` in Postgres), escaping `\`, `%` and `_`
  the same way the Oracle repository does.
- A duplicate NIK raises Postgres error `23505`. Both repositories translate their database's unique-violation
  error into `DuplicateKeyException`, so `CustomerService` returns 409 with either provider.
- The seed is a SQL script rather than `HasData`: `HasData` needs fixed ids, and with an identity column
  explicit ids leave the sequence at 1, so the first insert from the API would fail with a duplicate key.
  Running `seed.sql` again inserts nothing, but Postgres still consumes identity values for the skipped
  rows, so the next id jumps (gaps in ids are normal).

## Run the API with Postgres

```bash
dotnet run --launch-profile http --Database:Provider=Postgres
# or: export Database__Provider=Postgres
```
